# AutoDRIVE - Installer & ROS 2 Bridge (AIROS) 🏎️



This repository provides a detailed guide to installing the AutoDRIVE simulator and configuring the communication bridge between the AutoDRIVE Simulator and ROS 2 Humble. The goal is to enable control and data acquisition for the F1TENTH vehicle for robotics and autonomous navigation projects.

Following this guide top to bottom leaves you with a single self-contained workspace:

```
~/autodrive/f1tenth_ws/          # this repo, cloned
├── simulator/                    # simulator binary (downloaded, not tracked)
├── venv/                         # Python virtual environment (created, not tracked)
├── src/
│   └── autodrive_ros2/           # devkit ROS 2 bridge (cloned from upstream, not tracked)
├── build/ install/ log/          # generated by colcon (not tracked)
├── requirements.txt
└── README.md
```

Only `requirements.txt` and `README.md` (plus whatever ROS 2 packages you add yourself later, e.g. under `src/`) are meant to be version-controlled here. The simulator binary, the venv, and the upstream devkit source are all fetched/generated by the steps below — none of that belongs in git (it's either too large, not portable across machines, or someone else's repo).

## 🕹️ 1. Simulator Installation



The simulator binary lives inside this workspace, in `simulator/`, but it is **not** a ROS 2 package — it's a standalone Unity executable that talks to the bridge over a WebSocket. We keep it here for convenience only, and mark it so `colcon` never scans it.


1. **Download** the compressed file (.zip) of the simulator for Linux.
* ⬇️ [Download AutoDRIVE Simulator Linux](https://github.com/Tinker-Twins/AutoDRIVE/releases/download/Simulator-0.3.0/AutoDRIVE_Simulator_Linux.zip)

2. **Unzip it directly into `simulator/`:**

   ```bash

   cd ~/autodrive/f1tenth_ws

   unzip ~/Downloads/AutoDRIVE_Simulator_Linux.zip -d simulator

   ```

3. **Grant execution permissions** to the main binary:

   ```bash

   chmod +x ~/autodrive/f1tenth_ws/simulator/"AutoDRIVE Simulator.x86_64"

   ```

4. **Tell colcon to ignore this folder** (it has no `package.xml`/`setup.py`, but skipping the scan is faster and avoids surprises):

   ```bash

   touch ~/autodrive/f1tenth_ws/simulator/COLCON_IGNORE

   ```

5. **Test it starts** (you can close it again, this is just a sanity check):

   ```bash

   cd ~/autodrive/f1tenth_ws/simulator

   ./"AutoDRIVE Simulator.x86_64"

   ```


## 🛠️ 2. ROS 2 BRIDGE (DEVKIT)


### 2.1 Create and Activate the Virtual Environment (venv)

To avoid conflicts between the library versions required by the Devkit and the system defaults (Ubuntu 22.04), we use a Virtual Environment (venv), created **inside the workspace root**:

   ```bash

cd ~/autodrive/f1tenth_ws

# Create the environment

python3 -m venv venv



# Activate the environment (you must do this in every new terminal)
source venv/bin/activate

```

> ⚠️ **Never move or rename this folder (or the venv inside it) after creating the venv.** A venv is not relocatable: `venv/bin/activate` and every script pip installs into `venv/bin/` (including `colcon`, see below) get an absolute path baked in at creation time. If you move the workspace, those paths silently point to a location that no longer exists, `colcon` falls back to the system Python, and every symptom in section 2.3 below comes back. If you ever do need to relocate, delete `venv/` and recreate it fresh at the new path — don't copy/move it.

### 2.2 Install Dependencies

With the environment active, install everything from `requirements.txt` in one shot:
```bash

pip install --upgrade pip

pip install -r requirements.txt

```

This installs the bridge's Python dependencies (pinned to versions verified to work together — see comments in `requirements.txt` for why some are pinned) **and** `colcon-common-extensions`, on purpose, inside this venv.

**Why install `colcon` inside the venv, instead of the usual `apt install python3-colcon-common-extensions`?** If `colcon` lives outside the venv (the system-wide install), `colcon build` runs under the **system** Python even while your venv is "active" — that's just where the `colcon` executable is. The ROS 2 entrypoint scripts it generates (`autodrive_incoming_bridge`, `autodrive_outgoing_bridge`, etc.) get a hardcoded shebang `#!/usr/bin/python3`, the system interpreter, regardless of what's active in your shell — a shebang is an absolute path, it ignores `$PATH`/venv activation entirely. At runtime those scripts then fail with `ModuleNotFoundError: No module named 'attrdict'` (or `gevent`), because those packages only exist in the venv's `site-packages`. Installing `colcon-common-extensions` *inside* the venv (as `requirements.txt` does) makes `colcon build` run with the venv's Python, so the generated scripts point to `venv/bin/python3` from the start, and everything just works.

### 2.3 Exclude the venv from colcon's build scan

`colcon build` recursively scans the whole workspace for packages, including `venv/`. Some libraries (e.g. `setuptools`) ship internal test fixtures with their own `setup.py`, which colcon can mistake for a real package. Mark the venv as ignored:
```bash

touch ~/autodrive/f1tenth_ws/venv/COLCON_IGNORE

```

### 2.4 Critical Compatibility Patch


The attrdict library has incompatibilities with collection modules in Python 3.10+. To fix the import error without affecting the global system, apply this patch directly to the files inside your venv:
```bash

# Fix Mapping import error in attrdict
find ~/autodrive/f1tenth_ws/venv/lib/python3.10/site-packages/attrdict/ -name "*.py" -exec sed -i 's/from collections import Mapping/from collections.abc import Mapping/g' {} +



# Fix multiple import variants
find ~/autodrive/f1tenth_ws/venv/lib/python3.10/site-packages/attrdict/ -name "*.py" -exec sed -i 's/from collections import Mapping, MutableMapping, Sequence/from collections.abc import Mapping, MutableMapping, Sequence/g' {} +



```



### 2.5 Cloning and Organizing the Devkit Source



To ensure ROS 2 compiles correctly, we must extract only the necessary metapackage from the official repository and remove redundant files. This folder is **not** tracked by this repo — it's fetched fresh from upstream every time you set up a new machine, so you always get Tinker-Twins' latest devkit.


### Cloning the Repository:

Navigate to your workspace source folder and clone the Devkit:


```bash

cd ~/autodrive/f1tenth_ws/src

git clone --single-branch --branch AutoDRIVE-Devkit https://github.com/Tinker-Twins/AutoDRIVE.git

```



Extraction and Cleanup:


To avoid duplicate package errors during compilation, move the ROS 2 folder to the src root and delete the rest of the repository:
```bash

# Move the ROS 2 metapackage
mv ~/autodrive/f1tenth_ws/src/AutoDRIVE/ADSS\ Toolkit/autodrive_ros2 ~/autodrive/f1tenth_ws/src/



# Delete the original repository to avoid conflicts
rm -rf ~/autodrive/f1tenth_ws/src/AutoDRIVE

```



### 2.6 Compiling the Workspace



Once the src folder is organized, proceed to build the packages. Make sure the venv is active — this ensures `colcon` (installed in step 2.2, inside the venv) is the one that runs, so the compiled scripts point to the venv's Python instead of the system's.
```bash



# Return to workspace root
cd ~/autodrive/f1tenth_ws



# Activate environment and load ROS 2
source venv/bin/activate

source /opt/ros/humble/setup.bash



# Compile
colcon build --symlink-install



# Source the newly compiled workspace configuration
source install/setup.bash

```

**Sanity check:** confirm the build actually picked up the venv's Python before moving on:
```bash

head -1 ~/autodrive/f1tenth_ws/install/autodrive_f1tenth/lib/autodrive_f1tenth/autodrive_incoming_bridge

```
This should print `#!/home/<you>/autodrive/f1tenth_ws/venv/bin/python3`. If it instead prints `#!/usr/bin/python3`, `colcon` ran with the system Python — re-check that `colcon-common-extensions` is installed in the venv (step 2.2) and that the venv is active (`which colcon` should point inside `~/autodrive/f1tenth_ws/venv/bin/`), then remove stale artifacts and rebuild: `rm -rf ~/autodrive/f1tenth_ws/{build,install,log} && colcon build --symlink-install`.




## 🚀 3. Execution and Teleoperation



To start the system, follow this order strictly. We recommend opening independent terminals for each process.


### Step 1: Start the Communication Bridge
You have two modes depending on whether you need sensor visualization or want to save system resources:

> `PYTHONUNBUFFERED=1` below is **optional, not required** — the bridge works identically without it. `ros2 launch` pipes each node's output rather than attaching it to a real terminal, so Python buffers it by default and log/error messages can appear delayed or grouped together. Setting this makes them show up immediately, which helps while debugging, but skipping it doesn't break anything.

**Option A: Bridge with Visualization (RViz)**
Use this to see the LiDAR, camera feed, and the vehicle's 3D model while driving.
```bash

cd ~/autodrive/f1tenth_ws

source venv/bin/activate

source /opt/ros/humble/setup.bash

source install/setup.bash

export PYTHONUNBUFFERED=1  # optional, see note above

# Launches the bridge and opens RViz automatically
ros2 launch autodrive_f1tenth simulator_bringup_rviz.launch.py

```

**Option B: Simple Bridge (Headless)**
Use this if you only want to teleoperate the car without the graphical overhead of RViz.
```bash



cd ~/autodrive/f1tenth_ws

source venv/bin/activate

source /opt/ros/humble/setup.bash

source install/setup.bash

export PYTHONUNBUFFERED=1  # optional, see note above

# Launches only the communication bridge
ros2 launch autodrive_f1tenth simulator_bringup_headless.launch.py

```



### Step 2: Run the Simulator



Open a new terminal and launch the simulator:
```bash

cd ~/autodrive/f1tenth_ws/simulator

./"AutoDRIVE Simulator.x86_64"

  ```

Actions in the simulator:


* Click the antenna button (Disconnected) until it changes to Connected.

* Verify that the driving mode is set to Autonomous.



### Step 3: Keyboard Control (Teleoperation)



In a new terminal, run the node to control the car using keys:
```bash

cd ~/autodrive/f1tenth_ws

source venv/bin/activate

source /opt/ros/humble/setup.bash

source install/setup.bash

ros2 run autodrive_f1tenth teleop_keyboard

```

Controls: W (Accelerate), S (Reverse), A (Left), D (Right), X (Brake).


Note: You must keep this terminal window selected/focused for the vehicle to respond to keystrokes.
